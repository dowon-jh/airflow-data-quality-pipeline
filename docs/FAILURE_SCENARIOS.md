# Failure Scenarios

## 처리 정책

Phase 7의 정책 1.0 구현 후 Phase 8에서 5% PASS·6%/20% FAIL, 입력 오류·빈 입력·내용 충돌·DB 중단/재시도/복구·재실행·롤백·동시 처리를 실제 시연했습니다. [확정 실행 증거와 범위](PHASE8_FAILURE_RECOVERY.md). 아래는 시나리오 설계입니다. 동일 RAW 규칙 버전 변경 등 모든 확장 사례를 시연한 것은 아닙니다.

레코드의 품질 문제와 파이프라인이 정상 처리할 수 없는 문제를 구분합니다. 레코드 오류는 개별 행을 격리하고 가능한 데이터는 계속 처리합니다. 시스템·스키마·배치 수준 오류는 DAG를 실패시켜 잘못된 결과가 정상 산출물처럼 보이지 않게 합니다.

| 시나리오 | 기대 처리 | 기대 상태·증거 |
|---|---|---|
| 한 레코드에 NULL/잘못된 카테고리 | 해당 행 격리, 다른 정상 행 처리 | DQ 규칙 ID, `source_record_id`, `batch_id` 기록 |
| 동일 배치 내 중복 `product_id` | 중복 처리 정책에 따라 탐지 및 격리 | 대표/중복 행 기준과 탐지 건수 기록 |
| 원문과 OCR 텍스트 차이 | 불일치 신호 기록, 과도한 의미 판정 금지 | DQ009 발생 |
| 합성 품질 오류율이 임계치 초과 | Clean·Quarantine·마트 결과를 보존한 뒤 마지막 임계치 태스크 실패 | DAG가 실패하고 임계치와 실제 지표가 로그에 남음 |
| 필수 입력 컬럼 누락/타입 변경 | 스키마 검증에서 배치 중단 | 적재 단계가 실행되지 않고 누락 컬럼이 로그에 남음 |
| PostgreSQL 연결 실패 | 적재/조회 태스크 실패 및 제한된 재시도 | Airflow에 실패 상태와 연결 오류 표시 |
| 동일 배치 재실행 | 중복 결과를 만들지 않고 결과를 안전하게 교체 또는 upsert | Clean/Quarantine/Mart 건수가 첫 실행과 일치 |
| 수정된 입력 재처리 | 새 배치 ID로 RAW 적재, 기존 배치 보존 | 두 배치와 입력 해시 추적 |
| 동일 RAW에 규칙 변경 | 새 규칙 버전으로 재평가 | 규칙 버전과 처리 실행 식별자 기록 |
| 빈 입력 배치 | 첫 버전에서 오류로 중단 | RAW 적재기·DQ·분리 적재기가 명확한 실패를 반환 |

## 재처리 설계

- 모든 태스크는 `batch_id`로 입력 범위를 제한합니다.
- 결과 적재는 배치별 삭제 후 재적재를 한 트랜잭션으로 수행합니다. 성공 실행별 요약 이력은 누적하고, 현재 결과는 재실행해도 중복되지 않습니다.
- 새 분리 적재는 이전 마트를 같은 트랜잭션에서 무효화합니다. 마트는 배치 최신 집계로 교체하며 게이트 판정은 실행·정책별 이력을 보존합니다. 동일 run의 게이트 재시도는 같은 판정을 재사용합니다.
- 같은 RAW·같은 규칙 버전 재실행은 입력을 수정하지 않고 결과 중복 없이 처리합니다.
- 같은 RAW를 새 규칙 버전으로 재평가할 때는 규칙 버전·실행 식별자를 결과에 남깁니다.
- 입력 데이터를 수정하면 새 `batch_id`로 적재합니다. 기존 RAW는 유지합니다. 원 배치와의 연결 메타데이터 저장은 이후 결과 처리 단계에서 설계합니다.
- 품질 임계치 실패도 인프라 복구 후 같은 입력을 재실행하는 경우와 수정된 입력을 새 배치로 처리하는 경우를 구분합니다.
- 일부 태스크 성공 후 실패해도 RAW 원본과 실행 식별자로 상태를 추적할 수 있어야 합니다.

## 관측 가능성

각 DAG 실행 로그에는 최소한 `batch_id`, 입력 건수, 통과 건수, 격리 레코드 수, 규칙별 오류 수, 임계치, 최종 결정이 포함됩니다. 개인정보나 실제 업무 데이터는 쓰지 않습니다.

## 장애 시연 순서

1. 정상 분포 데이터로 전체 DAG 성공을 확인합니다.
2. 한 종류의 레코드 오류를 넣고 해당 행만 격리되는지 봅니다.
3. 모델 버전 하나의 오류율을 높여 배치 임계치 태스크가 실패하는지 확인합니다.
4. 같은 배치를 재실행해 중복 적재가 없는지 비교합니다.
5. 선택적으로 입력 스키마 오류와 DB 연결 오류의 Airflow 로그를 확인합니다.

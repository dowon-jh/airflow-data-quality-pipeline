## D-015: Phase 5 결과 교체와 성공 실행 이력 (2026-09-28)

- 상태: 확정·구현
- 결정: CLEAN·QUARANTINE·이슈에는 배치의 최신 결과만 저장하고, `clean.processing_run`에는 성공 실행별 요약·규칙 버전·UUID·DAG ID·최신 여부를 보관한다. 전체 과거 행 snapshot은 누적하지 않는다.
- 재실행: 같은 배치 새 UUID는 결과를 원자적으로 교체하고 요약 이력을 추가한다. 같은 현재 UUID는 내용·규칙·DAG ID·결과를 확인하고 추가 저장 없이 반환한다. 이전 UUID는 재사용하지 않는다.
- 동시성: RAW 적재와 분리 적재는 같은 배치 advisory lock을 사용한다. 결과 삭제·적재·최신 표시·이력은 한 트랜잭션으로 처리한다.
- 데이터: CLEAN의 ID·카테고리·속성은 정규화하며 QUARANTINE은 원본 업무 값을 유지한다. WARNING을 포함한 모든 이슈는 RAW FK로 연결한다.
- 이유: 결과 중복을 막으면서 수동 실행과 향후 DAG 실행의 처리 기준을 추적한다.

## D-016: Phase 6 태스크 경계와 재시도 (2026-09-28)

- 상태: 확정·구현
- 결정: `collect_input → load_raw → evaluate_quality → load_results`. 생성은 WSL 별도 명령. 수집 단계에 입력 스키마·manifest 검증, 품질 엔진에 정규화를 포함한다.
- 스케줄: 수동, catchup 없음, DAG 동시 실행 1개. 고정 파일을 주기적으로 재처리하는 자동 실행은 정기 입력 공급 구현 후 검토한다.
- 재시도: 인프라 예외는 2회·30초부터 지수 지연·최대 2분. 결정적 입력/계약 오류는 즉시 실패. 태스크 5분·run 20분 timeout.
- 추적: DAG ID·실제 run ID·batch ID로 UUID5 생성. 같은 run 재시도는 같은 처리 ID, 새 run은 새 처리 이력. superseded run은 새 run으로 처리한다.
- 데이터 계약: XCom에는 상대 경로·배치·해시·규칙 버전·집계만 전달. 결과 적재 시 RAW를 재평가하고 선행 품질 요약과 일치하는지 트랜잭션 안에서 비교한다.
- 이유: 기존 코드·RAW 불변·최신 결과 교체 정책을 재사용하고 task 재시도 중복과 입력 변경을 방지한다. Phase 7에서 집계·게이트 두 태스크를 추가해 현재 여섯 태스크이며 대용량 artifact는 범위 밖이다.

## D-017: Phase 7 집계와 게이트 정책 (2026-09-28)

- 상태: 확정·구현·정상 실행
- 차원: 배치·원천 UTC 날짜·정규화 카테고리·모델 버전. 생성 시각 NULL은 적재일로 대체하고 별도 건수 기록. NULL·빈 문자열·잘못된 차원을 보존한다.
- 보존: 배치 최신 마트·규칙 상세만 저장. 분리 적재가 결과를 교체할 때 이전 마트를 원자적으로 삭제. 성공 처리 UUID를 FK로 연결하고 집계와 게이트에 같은 배치 advisory lock 적용.
- 기준: 정책 1.0, 배치 전체 격리율 > 5%이면 FAIL. 정확히 5%는 PASS. Decimal 건수 비교. 그룹별/NULL 게이트는 추가하지 않고 해당 지표만 보관한다.
- 판정: 실행·정책별 PASS/FAIL 이력을 먼저 커밋한 뒤 FAIL이면 최종 DAG 태스크를 재시도 없이 실패시킨다. 판정 retry는 같은 PK를 재사용하며 기존 판정과 비교한다.
- 이유: 기본 합성 배치 4.1%를 허용하는 학습용 기준으로 품질 결과를 조사 가능하게 보존한다. 5%는 운영 SLA가 아니다. 이후 Phase 8에서 정확히 5% PASS·6%/20% FAIL을 실제 시연했다.

## D-018: Phase 8 검증과 증거 보존 (2026-09-28)

- 상태: 수행·검증 완료
- 입력: generated/phase8 아래 독립 suite ID·batch ID로 합성 입력을 추가하고 기존 두 배치를 삭제/교체하지 않는다.
- 장애: 실제 프로젝트 DB 서비스 중단, 태스크 재시도 소진과 복구. 결과/마트 commit 전 오류와 준비 작업 commit 전후 오류는 검증 프로세스의 일시적 Python patch로 주입한다. 운영 DAG에 장애 옵션은 추가하지 않는다.
- clear: 로컬 REST API로 명시적 run·task 목록을 preview하고 선택 범위를 확인한 뒤 clear한다. attempt 증가를 확인하며 검증 helper는 phase8__ run만 허용한다. 암호·JWT는 증거에 저장하지 않는다.
- 증거: 단계별 상태·집계·attempt·전체 행 hash 스냅샷·복구 결과를 generated JSON과 docs에 보존한다. 예상 DAG 실패는 검증 성공이며 예비 중단 묶음의 확인하지 못한 clear 판정은 제외한다.
- 결과: 확정 13개 run·기본 두 배치 내용 불변·준비 복구 PASS. 실무 확장과 timeout/대용량/crash/CVE 검증은 프로젝트 완성 후 별도 범위다.
